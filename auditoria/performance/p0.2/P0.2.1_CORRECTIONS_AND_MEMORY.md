# Boundless P0.2.1 — correções funcionais e evidência de memória

**Data:** 15/11/2026
**Branch:** `work/p0.2-performance-stabilization`
**Estado:** correções implementadas, compiladas e verificadas em runtime Forge de produção reduzido. A comparação de desempenho e a validação do cliente com o modpack completo continuam pendentes.

## Auditoria e estado inicial

O trabalho começou no commit `47f1806`, branch `work/p0.1-performance-baseline`. Foram mantidas no working tree as alterações preexistentes em configurações, scripts P0.1, `minecraftinstance.json`, resourcepacks e shaderpack. A instância usa Minecraft 1.20.1, Forge 47.4.28, Dayzombie Rebooted 1.0.5, Illage and Spillage: Respillaged 1.2.8, Boundless Tweaks 0.1.0 e Boundless Compat 0.1.1. O Java do build é o JDK instalado 17.0.12.

## Correções

### Dayzombie Rebooted 1.0.5

O bytecode de `SpawnerNaturalEntitySpawningConditionProcedure` confirma que o mod abre `config/dayzombiesconfig`, sem extensão. A instância tinha somente `config/dayzombiesconfig.json`. O `logs/latest.log` existente registra **649 `FileNotFoundException`** para o caminho sem extensão.

Boundless Fix cria `config/dayzombiesconfig` antes do setup comum somente quando Dayzombie está carregado e o arquivo ainda não existe. Usa primeiro o JSON já editado na instância e, na ausência dele, o padrão empacotado no JAR. Arquivos existentes são preservados. Os testes cobrem cópia, preservação, fallback e ausência do recurso padrão.

### Illage and Spillage: Respillaged 1.2.8

O log existente contém **1.548 erros para cada entidade**, `illageandspillage:bone` e `illageandspillage:axe`. A inspeção do JAR confirma que ambas são `AbstractHurtingProjectile`, mas as fábricas `lambda$static$30` e `lambda$static$40` as registram como `MobCategory.MONSTER`. O validador do Forge exclui `MISC` da verificação de atributos de mobs; a categoria errada fazia os dois projéteis aparecerem como entidades sem atributos durante validações do registro.

Boundless Fix muda somente as categorias desses dois projéteis para `MISC`, por mixin habilitado apenas para o mod ID `illageandspillage`, versão `1.2.8`. Não adiciona atributos artificiais nem altera as classes ou a lógica de lançamento. Os testes cobrem o gate de versão, as duas categorias e a preservação das demais.

Na primeira inicialização, o log mostrou que `BoundlessFixMixinPlugin` consultava `ModList.get()` antes de o Forge inicializar essa lista. O mixin falhou nessa etapa e, até o encerramento do cliente, surgiram 172 erros de atributos para cada projétil. O plugin foi corrigido para consultar `FMLLoader.getLoadingModList()` nessa fase e limitar a alteração à versão suportada. A nova build passou pelos 9 testes, incluindo uma regressão para a lista de mods ausente; o JAR corrigido foi instalado.

Um smoke test de desenvolvimento com `runClient` confirmou que o plugin reconheceu Illage 1.2.8, mas o harness terminou antes de aplicar os mixins do registro: o próprio `HurtByTargetGoalMixin` do JAR de Illage tentou encontrar o campo obfuscado `f_26032_` em classes de desenvolvimento MCP. Esse teste não validava a injeção de categorias.

### Validação em runtime Forge de produção

Em 15/11/2026, instalei um servidor Forge 47.4.28 descartável em `downloads/p0.2-forge-server-smoke-20261115` com o JDK 17.0.12 e um subconjunto de cinco JARs: Boundless Fix 0.1.0, Illage and Spillage: Respillaged 1.2.8, Dayzombie Rebooted 1.0.5, Citadel 2.6.0 e GeckoLib 4.8.4. O servidor iniciou em mundo separado; nenhum save do modpack foi aberto.

Com `-Dmixin.debug.verbose=true` e `-Dmixin.debug.export=true`, o log registrou que `IllageProjectileCategoryMixin` foi aplicado a `com.yellowbrossproductions.illageandspillage.init.ModEntityTypes`. A classe exportada pelo Mixin, inspecionada com `javap`, mostra `lambda$static$30` chamando o handler `boundlessFix$boneCategory` e `lambda$static$40` chamando `boundlessFix$axeCategory`; os handlers delegam para `IllageProjectileCategoryFix.category`. Como o seletor reconheceu a versão 1.2.8 e os testes cobrem o retorno `MISC` para `bone`/`axe`, isso confirma a transformação dos dois pontos no runtime empacotado. O servidor chegou a `Done (61.459s)` na primeira execução, com 49,111 ms registrados na preparação da região de spawn. Na execução de confirmação, o mundo já existente chegou a `Done (13.528s)`.

Trechos do log e do bytecode exportado:

```text
[14:45:27.812] Correcting Illage and Spillage projectile categories for 1.2.8.
[14:45:48.436] Mixing illage.IllageProjectileCategoryMixin from boundlessfix.mixins.json into com.yellowbrossproductions.illageandspillage.init.ModEntityTypes
[14:46:16.054] Done (13.528s)! For help, type "help"

lambda$static$30 -> modify$zza000$boundlessFix$boneCategory -> EntityType.Builder.m_20704_
```

No primeiro boot, o log confirmou a criação de `config/dayzombiesconfig`; os comandos de console `summon illageandspillage:bone 0 100 0` e `summon illageandspillage:axe 1 100 0` foram aceitos. No log da execução com exportação Mixin, as buscas retornaram zero ocorrências de `has no attributes`, falhas de injeção, falha de aplicação ou alvo não encontrado. A execução foi encerrada normalmente. Os tempos acima descrevem um servidor reduzido e uma região pequena de smoke test; não são comparáveis ao startup instrumentado do modpack nem medem TPS/MSPT.

O log preservado localmente em `downloads/p0.2-forge-server-smoke-20261115/logs/latest.log` tem SHA-256 `A85C83D14F6E820B6EF290AE78646E8963CDEB05DD4EF5F325EE30163E9BACC0`. O bytecode exportado fica em `.mixin.out/class/com/yellowbrossproductions/illageandspillage/init/ModEntityTypes.class` dentro desse diretório descartável.

O smoke test validou registro, transformação e spawn por comando dos projéteis. Não validou o lançamento por IA ou arma, colisão/dano, nem inicialização do conjunto completo de mods; o boot de cliente completo segue pendente.

## Evidência de alocação e GC

O arquivo [analysis.md](../../testes/2026-11-13/run6-live-v010-in-world/analysis.md) resume a gravação JFR preexistente `live-180s.jfr`; o [analysis.json](../../testes/2026-11-13/run6-live-v010-in-world/analysis.json) preserva os dados estruturados. Essa gravação é anterior às correções e não é um A/B controlado.

- Contadores JFR de alocação: **23,87 MiB/s** agregados em **207,68 s**; Render thread **15,86 MiB/s**, Server thread **6,81 MiB/s**. São deltas dos contadores cumulativos de bytes alocados, não memória residente.
- Foram registrados **4.849 eventos amostrados** de alocação. Sites/classes mais frequentes incluem `FileWatcher$WatcherThread.run` / `ConcurrentHashMap$ValueIterator` (468/474 amostras), `Direction.values` / `Direction[]` (208), `PoseStack.m_85836_` (159) e `Vec3` (159). Contagens de `ObjectAllocationSample` são amostras, não contagens exatas de objetos ou bytes; pesos isolados do JFR têm outliers e não foram usados para alegar volume por classe.
- As amostras de execução incluem **35 nomes de thread** associados a `AirPocketScanner`, com **111 amostras** no total. O bytecode do AmbientSounds 6.3.11 cria um `Thread` por scanner e consulta blocos/luz em `Level` fora da thread principal. É um candidato de contenção e compatibilidade para investigação; nenhuma mudança foi feita sem uma medição de impacto e análise de segurança.
- Na mesma gravação, `ServerTickTime` tem 144 médias intervalares: média **4.868 ms**, p95 **28.250 ms**, p99/máximo **33.332 ms**. São médias de intervalo, não duração de cada tick individual.
- GC nessa gravação curta: **3 pausas de coleta**, total **0,255 s**; quatro eventos de fase de pausa, máximo **144 ms**. Isso não representa as outras sessões: o JFR bruto de 1.184 s de `p01b-world-r2` registra **125 coletas**, **91,02 s** de pausas totais e pausa máxima de **39,404 s** (`G1Old`, `G1 Evacuation Pause`). Nesse arquivo, os contadores de alocação dão **82,45 MiB/s** agregados e `ServerTickTime` tem 771 médias intervalares, com média **630 ms**, p95 **3.129 ms**, p99 **5.276 ms** e máximo **7.954 ms**.
- Os CSVs da mesma sessão `p01b-world-r2` medem Private Bytes p95/máximo de **16,83/16,84 GiB**, working set p95/máximo de **7,25/7,75 GiB** e memória física livre mínima de **100 MiB**. O run foi marcado como inelegível para benchmark porque o Quick Play abriu um mundo novo em vez do `BC-Test`; esses dados ainda documentam pressão do processo e do host, mas não são comparação controlada.
- A captura P0.1 de inicialização, separada, mediu working set Java p95/máximo de **8,51/8,78 GiB**, memória física disponível mínima de **87 MiB** e commit de até **94%**. A redução de heap ou memória nativa precisa de A/B no mesmo mundo/rota, pois os arquivos atuais não separam com segurança heap, buffers diretos e outras reservas nativas.

## Comparação e limitações

Os dados “antes” de MSPT, FPS, GC e memória vêm das capturas P0.1. O marcador de inicialização P0.1 registrou **424,132 s**, acima da meta de 6 minutos. No primeiro boot real com o JAR inicial, o log marcou **535,746 s** até o cliente estar pronto; esse JAR ainda tinha o defeito no seletor de mixin, e o caminho do launcher não é equivalente ao baseline instrumentado. Portanto, não é uma comparação A/B. O runtime reduzido validou o JAR corrigido, mas não fornece uma comparação válida de startup, FPS, MSPT, TPS, GC ou memória. Esta etapa **não declara melhoria de desempenho mensurada**.

No primeiro boot, o caminho `config/dayzombiesconfig` não gerou ocorrência no log, consistente com o arquivo extensionless criado pelo bootstrap. As 87 `FileNotFoundException` restantes eram avisos de modelos de recursos ausentes (`minecraft:models/...`), não erros de configuração Dayzombie. O smoke test Forge posterior validou o mixin no servidor reduzido, mas ainda faltam benchmarks em mundo carregado, terreno existente/novo, shader ativo, renderização, chunks e sessão integrada de 30 minutos.
